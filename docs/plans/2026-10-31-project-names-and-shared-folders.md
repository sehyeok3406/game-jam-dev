# 프로젝트 이름 중복 방지와 공유 사본 폴더 이름 개선 계획

- 작성일: 2026-10-31
- 상태: 구현·검증 및 v0.41.0 커밋·푸시·배포 완료. 운영 폴더 이동·별도 운영 서버 갱신 미실행.
- 근거: 로컬·공유 프로젝트 이름을 중복 없이 사용하고, 탐색기에서는 ID 없이 프로젝트 이름만 표시하자는 사용자와의 논의.

## 1. 목표와 범위

이 PC의 프로젝트 목록에서 로컬·공유 프로젝트 이름을 함께 검사한다. 공유 프로젝트 사본은 `shared-workspaces/Project-PP/docs`처럼 사람이 읽을 수 있는 경로에 둔다. 전체 프로젝트 ID와 기존 목록 ID는 내부 식별에 유지한다.

```text
현재                                변경 후
shared-workspaces/                  shared-workspaces/
└─ f4f430e6-0236-…/                 └─ Project-PP/
   ├─ docs/                            ├─ docs/
   ├─ assets/                          ├─ assets/
   ├─ output/                          ├─ output/
   └─ .gamejam/                        └─ .gamejam/

앱 내부 목록: 기존 프로젝트 ID ↔ 이 PC의 실제 사본 경로
```

로컬 프로젝트는 사용자가 선택한 저장 위치를 유지한다. 새 로컬 프로젝트는 지금처럼 선택한 상위 폴더 아래에 프로젝트 이름으로 생성한다. 이번 폴더 위치 변경은 앱이 관리하는 공유 사본을 대상으로 한다.

## 2. 착수 전 구현에서 확인한 점

- `ProjectHomeService.create`는 이름의 형식을 검사하고, filesystem adapter는 같은 상위 폴더에 동일한 대상이 있으면 생성을 거절한다. 다른 위치의 로컬 프로젝트와 공유 프로젝트를 합친 이름 중복 검사는 없다.
- `ProjectLibrary`는 기존 registry 저장 큐와 안정적인 목록 ID를 가지고 있다. `SavedProject.localRoot`는 로컬에서 공유로 전환하기 전의 복귀 위치이므로 공유 사본 위치로 재사용하면 안 된다.
- 공유 사본 위치는 `shared-workspaces/<projectId>`로 계산한다. 접속·재시작·홈 탐색기·프로젝트 간 복사·휴지통 등에 같은 계산이 분산돼 있다.
- 로컬 이름 변경은 현재 metadata를 수정하며 실제 폴더는 이동하지 않는다. 공유 이름 변경은 관리자가 서버의 프로젝트별 명령 경계에서 확정한다.
- 초대 참여는 현재 `/join`에서 멤버를 먼저 생성하고 이름을 반환한다. 참여 전에 충돌을 확인하려면 사전 조회 계약과 최종 재검사가 필요하다.

## 3. 이름 규칙

### 대화에서 합의한 방향

1. 이 PC에 등록된 로컬·공유 프로젝트는 홈 분류 폴더와 저장 위치에 관계없이 이름을 함께 검사한다.
2. 폴더명에 ID·짧은 ID·자동 번호를 붙이지 않는다.
3. 충돌하면 “같은 이름의 프로젝트가 있습니다. 다른 이름을 입력해주세요.”라고 안내한다. 입력한 이름을 보존하고 이름 입력 위치로 돌려보낸다.
4. 생성뿐 아니라 이름 변경, 기존 폴더 등록, 공유 참여, 휴지통 복원, 로컬↔공유 전환에서도 확인한다.
5. 같은 프로젝트 다시 열기·재접속·같은 생성 요청 재시도는 자기 자신을 중복으로 판단하지 않는다. 기존 목록 ID를 유지하는 모드 전환도 동일하다.

### 구현 시 적용할 권장 세부 기준

- 앞뒤 공백 제거, 유니코드 NFC 정규화, 영문 대소문자를 무시한 비교 키를 공통 규칙으로 만든다. 내부 공백·의미 있는 문장부호는 임의로 제거하지 않는다.
- 생성과 이름 변경에 기존 `projectDirectoryName`의 길이·Windows 금지 문자·예약 이름 검사를 일관되게 적용한다. 사용할 수 없는 이름을 자동 치환하지 않는다.
- 오프라인·일시적으로 찾을 수 없는 프로젝트도 등록돼 있으면 이름을 사용 중인 것으로 본다.
- 휴지통의 프로젝트는 활성 이름 검사에서 제외하되, 복원 전에 이름과 목적지 충돌을 다시 확인한다. 충돌하면 활성 프로젝트의 이름을 먼저 정리하도록 안내하고 복원을 보류한다.
- 목록에 없는 파일·폴더가 목적지를 차지하고 있어도 덮어쓰거나 합치지 않는다. 같은 프로젝트의 중단된 작업인지 확인할 수 있을 때만 복구한다.
- 공유 서버는 자기 서버의 활성 공유 프로젝트 이름을 검사한다. 서로 다른 PC의 오프라인 로컬 프로젝트 전체에 대한 전역 유일성은 요구하지 않는다.

## 4. 생성·변경·참여 순서

```text
이름 입력 / 대상 이름 확인
    ↓
이름 형식 + 이 PC 전체 목록 + 실제 목적지 충돌 확인
    ↓
기존 작업 큐에서 이름 예약 및 최종 재검사
    ↓
필요한 서버 작업 확정 → 파일/목록 확정
    ↓
성공 표시 또는 기록을 사용한 복구
```

- **로컬 생성·기존 폴더 등록:** 중복 확인 뒤 생성/등록한다. 기존 폴더의 이름이 충돌하면 등록 전에 그 프로젝트 이름을 수정하는 절차를 제공하고 기존 등록 항목은 보존한다.
- **공유 생성·로컬에서 공유로 전환:** 이 PC에서 먼저 검사한 뒤 서버가 공통 이름 확정 경계에서 다시 검사한다. 두 사용자가 동시에 같은 이름을 요청해도 하나만 확정된다.
- **이름 변경:** 자기 항목을 제외하고 검사한다. 같은 이름을 다시 저장하는 요청은 중복 생성 없이 완료한다. 공유 이름 변경은 기존 관리자 권한을 유지한다.
- **공유 참여:** 초대 유효성·프로젝트 ID·이름·이름 버전을 최소한으로 사전 조회하고 이 PC 충돌을 검사한다. 최종 참여 시 서버가 조회한 대상과 이름 버전을 재검사한다. 이름이 바뀌었으면 멤버 생성 전에 재확인을 요구한다.
- **참여 충돌:** 사용자가 이미 가진 프로젝트의 이름을 먼저 바꾸도록 안내한다. 충돌하는 기존 항목도 공유 프로젝트이고 변경 권한이 없으면 해당 관리자에게 이름 변경을 요청해야 한다. 다른 팀의 이름을 자동으로 바꾸지 않는다.
- **응답 유실·저장 실패:** 기존 연결 준비/확정과 모드 전환 기록을 재사용한다. 서버 확정 뒤 PC 등록에 실패한 요청은 자격과 작업 기록을 보존해 재개한다. 실패를 감추기 위해 새 멤버·프로젝트를 다시 만들지 않는다.

구형 서버가 사전 조회 등 필요한 새 계약을 지원하지 않으면 해당 새 작업 전에 업데이트를 안내한다. 기존 프로젝트 열기와 문서 동기화의 호환 경로는 유지한다.

## 5. 공유 사본 경로 관리

- 공유 사본의 실제 경로를 registry의 별도 필드로 보관하고, 기존 목록 ID/프로젝트 ID로 조회한다. 기존 `localRoot`와 구분한다.
- 공통 경로 조회 port와 filesystem adapter를 마련해 접속·재시작·홈/MD 탐색기·복사 대상·캐시·휴지통·복원에서 재사용한다. 호출부가 프로젝트 이름이나 ID로 경로를 조합하지 않게 한다.
- 새 공유 사본은 이름으로 생성한다. 실제 폴더 소유권은 내부 프로젝트 식별 정보로 확인하므로 이름이 같다는 이유만으로 기존 자료를 연결하지 않는다.
- 같은 프로젝트의 서버 주소가 바뀌어도 기존 목록 식별과 사본 경로를 유지한다. 이름·주소를 프로젝트의 영구 식별자로 사용하지 않는다.
- ID는 목록/내부 관리 정보에 남는다. 인증 자료는 기존 OS 암호화 저장소에서 관리한다.

## 6. 기존 자료와 다른 PC의 이름 변경

### 기존 중복 이름

앱 업데이트로 기존 프로젝트를 삭제하거나 자동 개명하지 않는다. 먼저 중복 항목을 표시하고 사용자가 이름을 정리하게 한다. 기존 문서 열기·저장·동기화는 유지하고, 새 이름 확정과 폴더 전환에는 정해진 검사를 적용한다.

### 기존 UUID 폴더 전환

새 공유 사본은 이름 폴더를 사용한다. 기존 사본은 앱 업데이트만으로 일괄 이동하지 않고 프로젝트별 “공유 사본 폴더 이름 정리”에서 한 번 실행하는 방식을 권장한다.

1. 원래 프로젝트 ID·경로·목적지를 고정하고 중복과 폴더 소유권을 확인한다.
2. 미저장 편집·저장 큐·캐시를 보존하고 AI/모드 전환/삭제 작업이 유휴 상태인지 검사한다.
3. 감시를 일시 정지하고 이동 단계와 원래/새 경로를 영구 기록한다.
4. 문서·숨김 관리 자료·오프라인 초안·캐시·히스토리·개인 설정·추적되지 않은 보조 파일까지 폴더 전체를 이전한다.
5. registry와 경로 의존 설정·초안 키를 갱신하고 새 경로 검증 후 감시를 재개한다. 서버 문서 상대 경로와 ID는 유지한다.
6. 종료·파일 잠금·디스크 실패·외부 변경이 있으면 기록으로 이전 위치를 판단하고 재개한다. 다른 폴더에 합치거나 양쪽 사본 중 임의로 하나를 삭제하지 않는다.

경로를 저장하는 기존 설정·캐시·초안/저장 기록은 구현 착수 시 관련 호출부를 확인해 빠짐없이 연결한다. 이전 세션의 늦은 저장이 옛 폴더를 다시 만들지 않도록 시작 세션과 경로를 검증한다.

### 다른 PC에서 공유 이름이 바뀌는 경우

원격 관리자는 내 PC의 로컬 프로젝트 목록을 알 수 없다. 따라서 원격 변경으로 이름이 겹치는 경우는 완전히 예방할 수 없다.

- 서버의 확정된 이름과 이 PC의 경로/이름 적용 상태를 구분한다. 충돌·작업 중이면 기존 경로와 자료를 보존하고 정리를 보류한다.
- “공유 프로젝트 이름이 이 PC의 다른 프로젝트와 겹칩니다”라고 안내한다. 동기화는 프로젝트 ID로 이어간다.
- 사용자가 충돌 이름을 해소한 뒤 유휴 상태에서 폴더 이름을 반영한다. 공유 이름 변경은 팀 전체에 영향을 준다는 기존 권한과 안내를 유지한다.

이는 기존 자료와 외부 변경에 대한 이행 예외다. 이 PC에서 직접 실행하는 생성·등록·이름 변경은 계속 중복을 거절한다.

## 7. 책임 배치와 구현 순서

| 순서 | 작업                            | 소유 영역과 완료 기준                                                                                                                                                                |
| ---- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 이름·경로·충돌·이행 계약 정리   | `contracts`/`core`: 이름 정규화·자기 항목 제외·충돌 사유 계산. 설계 변경은 ADR과 관련 홈/파일/모드 문서에 기록                                                                       |
| 2    | 이 PC의 이름 확정 경계          | `application`/registry adapter: 기존 저장 큐에서 검사·예약·등록/변경 확정. 기존 폴더 등록과 복원·모드 전환 포함                                                                      |
| 3    | 공유 서버 이름과 참여 사전 조회 | server service/저장 경계: 생성·이름 변경·복원이 함께 쓰는 이름 확정 순서. 프로젝트별 FIFO만으로는 서로 다른 프로젝트 간 경쟁을 막을 수 없으므로 공통 순서를 정하고 실패 시 예약 해제 |
| 4    | 공유 경로 조회 통합             | desktop 조립과 filesystem adapter: 분산된 ID 경로 계산을 한 경계로 모으고 기존 사본 위치를 명시적으로 기록                                                                           |
| 5    | 새 이름 폴더와 기존 사본 전환   | `application` 이전 절차 + filesystem journal: 유휴 검사·자료 보존·재시작 복구·경로 참조 갱신                                                                                         |
| 6    | UI와 실제 패키지 확인           | 생성/이름 변경/참여/복원 안내, 홈과 MD 탐색기 표시, 다중 PC 충돌 및 이전 실패 처리 확인                                                                                              |

이름 검사만 UI에 추가하거나 탐색기 경로 한 곳만 변경한 중간 상태를 배포하지 않는다. 개인 로컬 기능에는 서버 연결이나 로그인을 요구하지 않는다.

## 8. 검증 및 완료 기준

- 로컬↔로컬·로컬↔공유·공유↔공유의 중복, 다른 저장 위치/홈 분류 폴더, 공백·대소문자·유니코드, Windows 금지 이름을 검사한다.
- 동시 생성·교차 이름 변경·자기 이름 재저장·재접속·응답 유실·서버 저장 실패에도 중복 확정과 이름 예약 유실이 없다.
- 참여 전 충돌은 신규 멤버/불필요한 사본을 남기지 않는다. 사전 조회 뒤 이름 변경과 확정 뒤 PC 실패도 각각 검증한다.
- 기존 중복·휴지통 복원 충돌·관리자 권한 부재·원격 이름 변경 충돌을 보존 중심으로 처리한다.
- UUID 폴더 전환 전후 실제 파일의 경로·내용·해시, 오프라인 초안·저장 큐·이미지·개인 설정·히스토리를 확인한다. 파일 잠금·강제 종료·재시작·외부 수정·프로젝트 전환 시 복구한다.
- 홈/MD 탐색기, 비활성 공유 프로젝트로 복사, 앱 재시작·서버 주소 변경, 로컬↔공유 전환, 휴지통/복원 모두 같은 실제 경로를 사용한다.
- TypeScript 변경은 `typecheck`, contracts/core 변경은 해당 strict 검사, 의존성과 경로 소유권 변경은 아키텍처 검사를 실행한다. 관련 홈·라이브러리·서버·모드·휴지통·프로젝트 파일 회귀와 실제 Windows 패키지 검사를 선택한다.

## 9. 구현 기록 · 2026-10-31

사용자의 구현 지시로 1~6단계를 구현했다. 공통 이름 검사·PC 예약/registry 확정·서버 공통 이름 큐, 참여/복구 사전 조회, durable 참여 재시도, sharedRoot resolver와 전체 폴더 이전 journal, 홈 충돌/정리 표시, 기존 폴더 등록 이름 수정/취소를 연결했다. 재접속은 기존 멤버·로컬 복귀 위치를 유지한다. 같은 서버/프로젝트 재가입의 사본 소유권을 확인하고 다른 서버의 동명 폴더는 거절한다. [ADR 0004](../architecture/decisions/0004-project-names-and-shared-folders.md)에 현재 정책과 기존 복구 응답 유실의 한계를 기록했다.

기존 Grok·AI 작업은 보존했다. 공통 파일에서 이번 변경과 겹친 부분은 collaboration-client, collaboration 계약, 회귀 안내뿐이며 그 외 기존 작업 파일 해시는 유지했다. 새 아키텍처 예외는 없고 해소한 home-service→home-organization 예외 1개를 제거했다.

검증 기록:

- 전체 자동 검사: `node --test --test-concurrency=4 tests/*.test.mjs` 1,065 통과·기존 native Grok 1건 skip·실패 0. 이전 기본 동시 실행에서 무관한 터널 시작 검사 1건이 실패했으나 단독 재실행과 제한 동시 실행 전체에서 통과했다.
- 최종 재가입 보완 후 `project-names`·`collaboration-session`·architecture 42건 통과. 이름 정리/초안/복원/홈 51건과 관련 layout·mode·copy·server 회귀 59건도 통과했다.
- root TypeScript, contracts/core strict 타입 검사, 아키텍처, 변경 파일 oxlint/oxfmt, diff 공백 검사 통과.
- 실제 Windows 패키지 빌드와 격리 profiles에서 홈 이름 정리·중복 생성 거절·초안/숨김 binary 보존·재시작 경로, native 폴더 선택·로컬↔공유 전환/소유권 인계, 프로젝트 간 local/shared 복사 회귀 통과.
- 마지막 연결/소유권 보완을 반영해 다시 빌드한 최종 패키지에서 session·home·project-copy 검사를 통과했다. 실제 참여/반복 참여/복구/탈퇴·원래 로컬 위치·오프라인 백업·UI 충돌 해결·공동 휴지통/히스토리/재시작을 확인했다.

검사에는 임시 폴더/서버/UUID 프로필만 사용했다. 실제 Project-PP 자료, 설치 앱, 운영 서버와 다른 PC는 변경하지 않았다. 커밋·푸시·배포는 이 작업에서 수행하지 않았다.
