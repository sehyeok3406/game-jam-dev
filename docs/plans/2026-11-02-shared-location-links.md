# 공유 프로젝트 위치 링크 구현 계획

- 작성일: 2026-11-02
- 상태: 2026-11-03 구현 및 핵심 검증 완료. 공개 배포와 실제 두 PC 검증은 별도이며 [구현·검증 기록](../audits/2026-11-03-shared-location-links.md)에 결과와 제약을 구분한다.
- 목표: 참여 자격이 있는 사용자가 외부에서 받은 링크를 열어 Game Jam!의 해당 프로젝트와 문서·그림·텍스트·HTML 위치로 이동한다.

- 배포: [v0.44.0 게시·공개 검증과 자동 업데이트 피드 반영 완료](../audits/2026-11-03-v0.44.0-release.md). 실제 두 PC·메신저 검증 등 남은 범위는 기록에서 구분한다.

## 사용자 동작과 범위

대상 우클릭 → `위치 링크 복사` → 메신저 등에 전달 → 상대방이 링크 열기 → 기존 참여 자격 확인 → 프로젝트/캔버스 전환 → 대상 중앙 배치와 일시 강조가 기본 흐름이다.

| 대상                      | 첫 구현의 동작                                                  | 후속 정밀 위치 지원                                 |
| ------------------------- | --------------------------------------------------------------- | --------------------------------------------------- |
| Markdown 문서/이미지 카드 | 문서 카드로 이동. 최소화·접힌 섹션은 기존 임시 펼침 동작 재사용 | 문서 내부 문단으로 스크롤·강조                      |
| 자유 그림·도형            | 선택한 그림 객체로 이동·강조                                    | 여러 획을 하나의 그림으로 공유하는 묶음은 별도 범위 |
| 캔버스 텍스트             | 텍스트 객체로 이동·강조                                         | 객체 내부 특정 문단으로 스크롤·강조                 |
| HTML 결과                 | 해당 미리보기 카드로 이동. 실행은 기존 미리보기 정책에 따름     | HTML 내부 요소 이동은 이번 기본 범위에서 제외       |
| 기타 프로젝트 파일        | 앱이 관리하는 파일만 허용하고 기존 보기/파일 표시 경로로 연결   | 임의 PC 파일·실행 파일 자동 실행은 지원하지 않음    |

특정 텍스트 위치의 기본 단위는 문단/블록으로 한다. 임의 문자 범위를 편집 후에도 영구 추적하는 기능과는 구분한다. 그림은 객체 단위이며 여러 펜 획이 자동으로 하나의 대상으로 묶인다고 보장하지 않는다.

첫 버전의 외부 공유는 온라인에서 서버가 현재 접근 권한을 확인할 수 있는 공동 프로젝트를 대상으로 한다. 개인 로컬 기능은 계속 서버·로그인과 독립적으로 동작한다. 로컬 프로젝트의 다른 PC 공유는 이 기능의 범위가 아니다.

## 현재 구현에서 재사용할 것

- `src/document-links.ts`: 현재 프로젝트 내부의 `gamejam://document/...`, `gamejam://file/...` 생성·해석. 외부 공유용 프로젝트 정보나 블록 위치는 아직 없다.
- `src/ui/workspace/WorkspaceScreen.tsx`: `openDocumentLink`, `jumpTo`, `pendingCanvasJump`와 캔버스 전환·선택·화면 맞춤. 문서·HTML·그림 위치를 찾는 코드가 있다.
- `src/contracts/drawing-types.ts`: 그림·도형·텍스트에 공통 객체 ID와 캔버스 소속이 있다.
- `src/contracts/documents.ts`: 문서 ID 또는 경로 기반 식별. 본문은 Markdown 문자열이며 영속 블록 ID 계약은 없다.
- `src/result-structure.ts`: HTML 결과 카탈로그의 ID·현재 경로·이전 경로. 경로 변경에 대응할 수 있는 기반이지만 모든 레거시 HTML에 ID가 있다고 가정하지 않는다.
- `src/project-library.ts`: 암호화된 참여 자격과 공동 프로젝트 목록. `findShared`는 정확한 주소 외에 단일 프로젝트 ID 일치로도 찾으므로 외부 링크의 서버 검증 없이 그대로 사용하지 않는다.
- `ProjectHomeService`, `DesktopProjectSessions`, `DesktopCollaborationSessions`: 프로젝트 열기·저장 보존·인증된 재연결·세션 전환.
- 주입된 UI runtime과 기존 clipboard/preview API: 화면에서 Electron이나 파일 구현을 직접 호출하지 않는다.

현재 확인한 main/패키징 설정에는 외부 `gamejam://` 처리와 single-instance 전달 경로가 없다. 앱 내부 링크 인식과 Windows 프로토콜 등록은 별개의 작업이다.

## 1단계: 링크 계약과 정책 확정

공유 링크에 버전·프로젝트 ID·대상 종류·대상 ID/프로젝트 상대 경로를 넣고, 필요한 경우 서버 식별 힌트와 캔버스 힌트를 넣는다. 아래 주소는 제안 예시다.

```text
gamejam://open?v=1&project=<project-id>&kind=document&id=<document-id>
```

- 기존 내부 문서 링크 형식은 계속 해석한다. 기존 내부 링크를 외부 공유용 링크로 오인하지 않는다.
- 인증 토큰·초대 코드·복구 키·PC 절대 경로·본문은 주소에 넣지 않는다. 링크로 자동 참여하거나 새 자격을 만들지 않는다.
- 받는 PC의 저장된 공동 프로젝트 자격으로 대상을 해결한다. 프로젝트 이름·목록 ID·저장 폴더 이름으로 다른 PC의 프로젝트를 찾지 않는다.
- 서버 주소는 신뢰 근거가 아니다. 링크의 주소로 기존 토큰을 전송하거나 저장된 주소를 자동 변경하지 않는다. 저장된 연결과 프로젝트 ID를 확인하고 후보가 여러 개면 명시적으로 선택하게 한다.
- 동적인 내장 서버 포트·Cloudflare 주소 변경은 기존 연결 정보 갱신 경로로 처리한다. 고정 서버 식별자가 없는 현재 구조에서 주소 변경 후의 무조건적인 자동 연결은 보장하지 않는다.
- 문서는 영속 ID를 우선하고, 경로 기반 문서/레거시 파일에는 상대 경로 링크를 허용하되 이동·개명 후 끊길 수 있음을 명시한다.
- HTML은 카탈로그 ID가 있으면 재사용한다. 없는 파일의 ID 부여는 기존 저장/권한/히스토리 경계 안에서만 처리하며, 읽기 전용 사용자는 경로 기반 링크로 제한할 수 있다.
- 그림/텍스트의 ID를 기준으로 현재 캔버스를 조회한다. 캔버스 ID는 힌트로만 쓰고 이동 후의 실제 소속을 우선한다. 중복·모호한 ID는 임의 선택하지 않는다.
- 삭제 후 같은 경로에 생성된 파일, 복제본, 다른 프로젝트로 복사한 항목을 원래 대상이라고 취급하지 않는다. 경로 링크의 동일성 보장 한계도 함께 표시한다.

완료 기준: 버전·종류별 계약, 오류 코드, 호환 규칙, ID 보존/복제/삭제/복원 정책을 문서화한다. 외부 프로토콜과 세션·권한 경계를 다루므로 구현 시 ADR과 관련 설계 문서를 함께 갱신한다.

## 2단계: Windows 링크 수신과 프로젝트 열기

- 설치된 앱에 `gamejam` 프로토콜을 등록한다. 설치·업데이트·제거 및 여러 설치본의 처리 주체를 확인한다.
- 종료 상태에서는 최초 실행 인자로, 실행 중에는 기존 앱으로 전달되는 이벤트로 링크를 받는다.
- renderer/runtime 준비 전 링크는 제한된 대기열에 보관하고 준비 완료 뒤 전달·처리 결과를 확인한다. 중복 전달은 중복 전환을 만들지 않는다.
- 현재 별도 테스트 사용자/프로필 실행이 있으므로 무조건적인 전역 단일 인스턴스로 막지 않는다. 프로필별 잠금과 기본 설치 앱의 수신 주체를 설계하고 격리 프로필을 유지한다.
- 같은 프로젝트면 현재 세션에서 대상을 해결한다. 다른 프로젝트면 기존 편집 flush·프로젝트 보존·열기 순서를 사용한다.
- 미저장 작업·오프라인 미전송 변경·AI 실행 등 기존 전환 차단 조건을 따른다. 막힌 상태에서는 전환하지 않고 재시도 가능한 안내를 제공한다.
- 저장된 참여 자격과 서버의 기존 인증된 state/lifecycle 조회로 접근 가능 여부를 확인한다. 우선 새 공개 링크 해석 서버나 별도 인증 경로는 만들지 않는다.
- 참여 기록 없음·자격 만료/회수·프로젝트 휴지통·서버 연결 실패를 구분한다. 외부 링크를 여는 과정에서 온라인 권한 확인이 안 되면 캐시로 성공 처리하지 않는다.
- 요청 ID와 시작/활성화 세션을 확인한다. 수동 프로젝트 전환이나 새 링크가 이전 요청을 대체하면 늦은 결과가 새 화면을 바꾸지 않도록 한다.

완료 기준: 다른 앱에서 링크를 열었을 때 앱 종료/실행/홈/다른 프로젝트 상태 모두에서 올바른 프로젝트로 한 번만 이동하고, 실패 시 편집 상태를 보존한다.

## 3단계: 모든 객체 링크와 복사 UI

- 문서·HTML·그림·텍스트의 단일 대상 메뉴에 `위치 링크 복사`를 추가한다. 읽기 권한 사용자도 영속 데이터를 수정하지 않는 링크 복사는 사용할 수 있다.
- 공유가 확정되지 않은 신규 항목은 기존 저장·동기화 경로의 완료를 확인한 뒤 링크를 발급한다. 실패·충돌·세션 교체 시 복사 성공으로 표시하지 않는다.
- 일반 복사·프로젝트 간 복사와 별도 메뉴로 구분한다. 다중 선택에서 임의로 하나의 링크를 복사하지 않는다.
- `jumpTo` 기반의 이동을 작은 UI navigation 모듈/hook으로 정리해 내부 링크·외부 링크가 함께 사용한다. 업무 순서를 `WorkspaceScreen`에 추가로 집중시키지 않는다.
- 대상의 실제 캔버스 전환 → 노드 생성 확인 → 임시 펼침 → 화면 맞춤 → 짧은 강조 순서로 처리한다. 고정 시간 지연만으로 준비 완료를 판단하지 않는다.
- HTML은 링크 열기만으로 게임 실행·외부 네트워크·외부 앱 실행을 새로 유발하지 않도록 기존 미리보기 정책을 유지한다.
- 링크를 클릭 가능한 형태로 표시하지 않는 메신저에 대비해 앱에 `위치 링크 열기/붙여넣기` 진입점을 제공한다. HTTPS 안내 사이트는 별도 선택 확장으로 남긴다.

완료 기준: 서로 다른 PC/격리 사용자에서 문서·이미지·자유 그림·도형·캔버스 텍스트·HTML을 공유하고, 다른 캔버스/접힌 대상까지 정확히 찾는다.

### 화면 이동과 크기별 배율 정책

- 기준은 이미지 파일의 원본 해상도가 아니라 캔버스에서 실제 표시되는 대상의 경계다. 회전한 도형은 회전 후 보이는 경계를 사용하고, 패널·도구 영역을 제외한 가용 화면에 맞춘다.
- 도형·이미지·그림은 전체 경계와 주변 여백이 보이도록 중앙 배치한다. 큰 대상에 고정 최소 배율(예: 25%)을 적용해 일부만 잘라 보여주지 않는다. 필요하면 그보다 더 축소한다. React Flow의 기본 최소 배율 때문에 전체 맞춤이 막히는지도 실제 구현에서 확인한다.
- 작은 대상은 자동 확대의 상한을 우선 100%로 둔다. 그 상태에서도 작은 점·가는 획은 화면상 일정 최소 크기의 외곽 강조 표시로 위치를 알린다. 객체 자체의 저장 크기나 좌표는 바꾸지 않는다.
- 매우 큰 이미지의 세부 내용은 사용자가 도착 뒤 확대해서 확인한다. 처음부터 임의의 중앙 일부를 보여주지 않는다.
- 문서·텍스트·HTML은 읽기 가능한 배율과 내부 스크롤을 우선한다. 문단 링크는 해당 문단, 문서 자체 링크는 시작 부분을 보여주는 방향으로 조정한다. 이미지 카드처럼 시각 자료가 주된 대상은 위의 전체 맞춤 정책을 적용한다.
- 이동 애니메이션은 기존 약 300ms를 출발점으로 하며 여백·강조 최소 크기·확대 상한은 실제 화면 QA에서 확정한다. 수동 확대·이동을 시작한 뒤에는 링크 처리의 늦은 재측정이 화면을 다시 끌어당기지 않는다.
- QA에는 극소 점/획, 극대 이미지, 긴 가로/세로 이미지, 회전 도형, 작은 창/열린 사이드 패널, 대상 로딩 후 크기 확정을 포함한다. 극단적인 크기나 잘못된 경계로 배율 계산이 불가능하면 임의 위치로 이동하지 않고 안내한다.

## 4단계: 문서·텍스트 내부의 문단 링크

객체 링크가 동작한 뒤 수행한다. 이 단계까지 완료해야 문서 안의 특정 텍스트 위치 공유를 지원한다고 보고한다.

1. 작은 저장/재열기 실험으로 Markdown 블록 ID 표현을 확정한다. 본문의 명시적 앵커와 공유 metadata 분리 방식을 비교하되, metadata만으로 수정된 문단의 정체성이 자동 유지된다고 가정하지 않는다.
2. Tiptap의 Markdown 읽기/쓰기, 읽기 화면, 원문 편집, AI 본문 교체에서 ID가 보존되는지 확인한다. 표·목록·인용·코드 블록에서도 원문 손상과 불필요한 전체 재작성이 없어야 한다.
3. 캔버스 텍스트는 기존 직렬화된 Tiptap 문서와 validator에 블록 ID를 통합한다. 구버전이 속성을 제거하는지 확인하고 필요한 capability 협상/쓰기 제한을 마련한다.
4. 블록 복제는 새 ID, 이동은 기존 ID 유지로 정하고, 분할/병합·삭제·Undo/Redo·히스토리 복원·프로젝트 간 복사의 규칙을 정한다. 실제 저장 데이터와 서버 검증에 반영한다.
5. 영속 ID 부여는 편집 명령이므로 기존 잠금·revision·저장 큐·히스토리를 사용한다. 읽기 권한 사용자는 이미 저장된 앵커만 공유하고, 없는 경우 객체 링크를 제공한다.
6. 링크에 블록 ID를 추가하고 문서 준비 뒤 해당 문단으로 스크롤·강조한다. 블록이 삭제되었거나 외부 편집으로 ID가 사라지면 문서까지 이동한 뒤 위치를 찾지 못했다는 안내를 한다. 비슷한 문장을 임의로 정답으로 선택하지 않는다.

문자 일부의 정확한 강조는 후속 기능이다. 필요하면 인용문·앞뒤 문맥·본문 버전을 추가해 단일 일치를 확인하되, 편집 후에도 같은 문자 범위를 영구 보장한다고 안내하지 않는다. 임의 HTML 내부 요소의 영속 추적도 별도 설계가 필요하다.

완료 기준: 문단 앞에 글을 추가하거나 대상 문단을 이동해도 같은 문단을 찾고, 삭제/모호한 위치는 잘못된 곳을 강조하지 않는다. Markdown 왕복 저장과 공동 동기화에서 ID가 보존된다.

## 책임 배치

| 계층          | 추가할 책임                                                                      |
| ------------- | -------------------------------------------------------------------------------- |
| `contracts`   | 위치 링크 DTO·버전·대상/오류 종류·runtime/IPC 계약                               |
| `core`        | URL 생성/해석·길이/형식/상대 경로 검사·순수 대상 매칭·앵커 규칙                  |
| `application` | 자격 조회·접근 확인·프로젝트 전환·요청 취소/세션 검증·실패/재시도 조정           |
| `adapters`    | 기존 ProjectLibrary/파일/통신 port 연결. 영속 앵커 도입 시 기존 저장 구현 확장   |
| `desktop`     | OS 프로토콜·최초 실행/기존 인스턴스 전달·큐·preload/IPC·조립                     |
| `server`      | 기존 프로젝트 권한·상태 검증 유지. 새 앵커 데이터에 필요한 검증/호환 협상만 추가 |
| `ui`          | 메뉴·클립보드 호출·링크 붙여넣기·대기/오류·캔버스 이동·스크롤/강조               |

새 코드에서 `src/shared.ts`를 import하지 않는다. 기존 내부 문서 링크를 재사용하는 과정에서 레거시의 parser 의존이 순수 core로 유입되지 않도록 공통 URL 계산부터 분리한다. 별도 저장·인증·동기화 경로를 만들지 않는다.

## 검증과 완료 조건

- 자동 검사: `npm run typecheck`, `npm run typecheck:contracts`, `npm run typecheck:core`, `npm run lint`, `npm test`. `npm test`에 architecture 검사가 포함되므로 같은 소스에서 `test:architecture`를 중복 실행하지 않는다. 예외 완화로 통과시키지 않는다.
- 핵심 단위 검사: URL 왕복·기존 내부 링크 호환·버전 오류·경로 이탈/잘못된 인코딩·서버 혼동·토큰 비노출·대상 없음/중복·늦은 응답·연속 링크/수동 전환·저장 실패.
- 실제 임시 협업 서버: 관리자/편집자/읽기 권한·권한 회수·미참여·서버 중단·주소 갱신·공유 저장 확정·대상 삭제/복원·같은 이름의 다른 프로젝트.
- UI 회귀: 기존 `test:document-links:ui`, 그림/텍스트 UI, HTML preview UI와 프로젝트 세션/저장 검사에서 변경 범위에 맞는 항목을 선택한다. 4단계에서는 한글 조합 중 입력과 Markdown 왕복도 포함한다.
- Windows 실제 패키지/설치: OS 프로토콜 연결·종료/실행 중 수신·업데이트 후 연결·테스트 프로필 공존·프로젝트/캔버스 전환을 확인한다. Electron 개발 실행이나 이벤트 mock 통과로 설치 연동 완료를 주장하지 않는다.
- 두 PC 검증: 서로 다른 폴더와 저장된 참여 자격을 가진 두 환경에서 링크 전달을 확인한다. 한 PC의 두 프로필 검사와 실제 두 PC 검증 결과를 구분한다.
- 메신저 클릭 가능 여부는 실제 사용할 전달 앱에서 확인한다. 붙여넣기 경로도 함께 검증한다.

단계별로 구현 동작·실행한 검사·ID/주소 변경 등 남은 제약은 [구현·검증 기록](../audits/2026-11-03-shared-location-links.md)에 남긴다. 문단 앵커는 Markdown의 보이지 않는 inline 주석과 텍스트 JSON atom으로 확정했다. 같은 문서 내부 복제는 사본의 앵커 ID를 새로 발급하고, 부모 문서/텍스트 객체의 복제는 새 부모 ID로 원본 링크와 구분한다. 실제 설치/업데이트/제거·두 PC·메신저 전체 검증은 현재 완료 범위와 구분한다.
