# Game Jam! 고객군별 비즈니스 모델 캔버스 · 린 캔버스

작성일: 2026-10-26 · 상태: 사업 시작 전 검토용 1차 가설

목적은 현재 기능을 소개하는 데서 끝내지 않고, 놓친 사업 조건과 유료 수요의 불확실성을 드러내는 것이다. 고객군과 사업 규모를 지금 확정하지 않는다. 네 가지 고객군을 비교하되, 개인 무료 사용과 유료 구매자를 구분한다.

## 1. 지금까지 확인한 사실과 확인하지 못한 것

### 사용자가 직접 설명한 내용

- 여러 게임 기획 문서를 전환하거나 화면을 나누며 작업하는 불편을 줄이고 싶다. 무한 캔버스에서 문서를 메모지처럼 펼치고 시각적으로 배치하는 경험이 핵심 가치다.
- 짧은 아이디어를 AI로 시스템 문서로 정리하고, HTML 시제품으로 만들어 특정 기능과 프로토타입을 빠르게 확인하려 한다.
- 지원하는 개인 AI 연결을 활용해 기본 사용에 별도 앱 이용료를 요구하지 않는 방향이다. AI 계정 자체의 비용과 사용 한도는 별개다.
- 수익화 대상은 우리가 서버를 운영하는 공유 프로젝트다. Render를 운영 후보로 검토 중이다.
- 함께 게임을 개발하는 초보 수준의 기획자가 잠깐 체험했다. 구체적인 효용·불편·재사용 의사·구매 의사를 자세히 묻지는 않았다.
- 우선 고객군, 가격과 과금 단위, 목표 사업 규모는 미정이다. 고객군별 여러 버전을 비교하고 싶다.

### 저장소 문서로 확인한 제공 범위

현재 설명의 근거는 [프로젝트 설명](../../PROJECT_AI_BRIEF.md), [아키텍처 안내](../architecture/README.md), [AI 연결](../../AI_CONNECTION.md), [Render 운영 준비](../operations/render.md)다. 이번 문서 작성에서는 앱과 서버를 실행해 기능이나 운영 용량을 재검증하지 않았다.

- Windows 데스크톱 앱에서 캔버스·문서·자료와 HTML 시제품을 다룬다.
- 개인 로컬 기능은 서비스 로그인·구독·서버 연결에 종속시키지 않는다.
- 공동 작업은 팀원 요청과 관리자 승인 후 관리자 PC에서 AI를 실행하는 구조다. 서버가 AI를 대신 실행하는 구조가 아니다.
- 현재 안내된 AI 연결은 Codex CLI, Claude Code, Gemini CLI다. 모든 AI 구독이나 모든 모델이 연결된다고 가정하지 않는다.
- 읽기 전용 웹 게시와 향후 웹 편집기는 제공 단계가 다르다.
- 운영형 서비스의 계정·구독·결제와 상용 운영 준비가 모두 완료됐다고 판단하지 않는다.

### 아직 근거가 없는 주장

실제 고객 수, 활성 팀 수, 반복 사용률, 구매 의사, 적정 가격, 고객 확보 비용, 팀별 원가, 문의 대응 시간과 시장 규모는 미확인이다. 체험은 수요 검증이나 구매 증거로 계산하지 않는다. 창업자의 실제 불편과 효용은 문제 탐색의 출발점이며 시장 전체의 대표 증거는 아니다.

아래의 고객 요구·채널·관계·판매 방식·지표는 검증할 가설이다. 특히 교육·행사 상품은 현재 출시된 기능이나 확정된 개발 약속이 아니다.

## 2. 사업 규모는 지금 결정하지 않아도 된다

사업 규모는 캔버스를 작성하는 선행 조건이 아니다. 규모별로 성립 조건을 비교한 뒤, 유료 수요와 운영 부담을 보고 선택할 수 있다.

| 관점           | 부업으로 유지                       | 혼자 전업으로 유지                      | 직원을 고용해 성장                                  |
| -------------- | ----------------------------------- | --------------------------------------- | --------------------------------------------------- |
| 성공 기준      | 제한된 시간으로 추가 수입을 남긴다  | 본인의 생활과 지속 개발을 감당한다      | 여러 사람의 비용과 재투자를 감당한다                |
| 고객 선택      | 접근하기 쉬운 좁은 고객군부터 시작  | 반복 사용·갱신하는 고객군이 중요        | 더 큰 고객 풀이나 높은 계약 단가가 필요             |
| 상품 범위      | 운영과 지원이 적은 좁은 범위        | 반복적인 도움 없이도 쓸 수 있는 흐름    | 교육·영업·지원·운영을 다른 사람이 맡을 수 있는 구조 |
| 주요 위험      | 매출보다 지원 시간이 커짐           | 이탈과 신규 유입 정체로 소득이 불안정   | 채용 비용과 고객 확보 비용을 매출이 따라가지 못함   |
| 지금 확인할 것 | 소수 팀이 실제 돈을 내고 사용하는가 | 다음 작업과 다음 달에도 계속 사용하는가 | 반복 가능한 판매·지원과 충분한 수요가 있는가        |

### 설명용 계산: 가격 제안이나 매출 예측이 아니다

다음은 필요한 고객 수가 어떻게 달라지는지 보여 주기 위한 가정이다. Render의 실제 견적이나 측정한 원가가 아니다.

- 팀당 월 요금: 50,000원
- 팀 하나가 늘 때 추가되는 월 현금 비용: 10,000원
- 팀 수와 별개로 드는 월 고정 현금 비용: 200,000원
- 팀당 비용 차감 후 남는 금액: 40,000원
- 예시 산식: 필요 유료 팀 수 = 올림((고정 현금 비용 + 확보하려는 월 예산) ÷ 팀당 남는 금액)

| 설명용 시나리오         | 월 확보 예산 | 필요한 유료 팀 수 |       월매출 |
| ----------------------- | -----------: | ----------------: | -----------: |
| 추가 수입 예시          |    500,000원 |              18팀 |    900,000원 |
| 혼자 전업 예시          |  3,000,000원 |              80팀 |  4,000,000원 |
| 인건비·운영·재투자 예시 | 10,000,000원 |             255팀 | 12,750,000원 |

확보 예산은 세후 개인 소득이나 순이익이 아니다. 세금·환불·실제 결제 수수료·지원 인건비와 개발 시간을 별도로 반영해야 한다. 마지막 행은 여러 비용에 배정할 예산이며 특정 인원 고용이 가능하다는 뜻이 아니다. 개인 무료 이용자의 비용도 유료 고객이 함께 감당해야 한다면 추가한다. 서버 한 대가 이 팀 수를 수용한다는 의미도 아니다.

같은 가정에서 팀 요금이 30,000원이면 월 300만원 예산 확보에 160팀, 100,000원이면 36팀이 필요하다. 그러나 가격을 높이면 같은 수의 고객이 구매한다는 보장은 없다. 가격과 전환율은 함께 검증한다.

Render에서는 영구 디스크를 유료 서비스에 연결하며, 디스크를 연결한 서비스는 여러 인스턴스로 확장할 수 없고 재배포 중 중단된다. 따라서 현재 단일 서버 구상으로 작은 실사용을 검증하되, 성장 시 비용과 가용성 요구를 다시 판단해야 한다. [Render 영구 디스크 공식 문서](https://render.com/docs/disks)

## 3. 공통 제품 가치와 유료 전환 가설

공통 가치 제안 초안:

> 게임 기획 문서와 아이디어를 한 화면에 펼쳐 생각을 정리하고, 필요한 자료를 AI에 연결해 바로 플레이할 수 있는 시제품으로 확인하는 작업 공간.

운영형 공유 프로젝트의 가치 제안 초안:

> 팀이 별도 협업 서버를 운영하지 않고 같은 기획 자료와 시제품을 함께 다루며, 변경과 결과를 이어 가는 팀 작업 공간.

가장 중요한 미검증 연결은 다음과 같다.

> 개인 작업의 편리함 → 팀원을 초대할 필요 → 여러 사람의 반복 사용 → 운영형 공유 프로젝트에 실제 결제 → 갱신

무료 기능이 유용하다는 반응만으로 이 연결이 성립했다고 판단하지 않는다. 팀이 개인 작업 결과를 다른 무료 도구로 공유해도 충분하다면 유료 전환 이유가 약하다.

## 4. 버전 A: 개인 게임 기획자·개인 제작자

초보 기획자도 포함하지만 초보만을 대상으로 확정하지 않는다. 이 버전은 현 사업모델에서 주로 무료 사용과 팀 유입을 설명한다. 혼자 계속 쓰는 고객에게 독립적인 유료 상품을 임의로 추가하지 않는다.

### 비즈니스 모델 캔버스 A

| 구성 요소     | 초안                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 고객 세그먼트 | 문서를 시각적으로 정리하고 작은 게임 시스템을 직접 확인하려는 개인 기획자·개발자. 지원 AI를 직접 실행할 환경을 마련할 수 있는 사용자. |
| 가치 제안     | 여러 문서를 공간에 펼쳐 비교하고, 메모에서 기획 문서와 플레이 가능한 시제품까지 이어 간다. 개인 기본 사용은 무료다.                   |
| 채널          | 실제 게임 제작 사례, 짧은 작업 시연, 개인 개발자·기획자 커뮤니티, 동료 추천을 시험한다. 기존 유입 규모는 미확인이다.                  |
| 고객 관계     | 스스로 시작할 수 있는 예제·안내를 제공하고 초기 체험을 관찰한다. 무료 사용자 문의가 과도하게 늘지 않는 지원 범위를 설계한다.          |
| 수익원        | 단독 무료 사용 자체의 매출은 0원. 팀을 구성하고 운영형 공유 프로젝트로 전환할 때 유료 모델 B와 연결된다. 전환율은 미확인이다.         |
| 핵심 자원     | 캔버스·문서 편집 경험, 게임 기획 맥락, AI 연결·결과 검증, 실행 예제와 안내 자료.                                                      |
| 핵심 활동     | 첫 기획·첫 시제품 성공률 개선, 편집·저장 안정성 유지, 실제 사용 관찰, 지원 AI 변경 대응.                                              |
| 핵심 파트너   | 사용자 선택 AI 제공자와 CLI 생태계. 실제 제휴 계약이 있다는 뜻은 아니다. 커뮤니티·교육자는 향후 유입 협력 후보.                       |
| 비용 구조     | 앱 개발·유지보수·배포·문서·사용자 지원. AI를 사용자 계정으로 실행해도 앱 운영자의 비용이 사라지지는 않는다.                           |

| 채널                 | 게임 기획의 실제 전후 사례와 커뮤니티 체험 모집을 시험한다. 사용자의 기존 연락망은 미확인이다.                                                                                                                  |

| 비용 구조            | 개발 시간, AI 연결 설치 지원, 오류·생성 실패 문의, 무료 이용자 유지비.                                                                                                                                          |

기존 대안은 현재 문서 도구와 AI 채팅·코딩 도구를 조합하는 방식, Obsidian Canvas 같은 공간형 문서 도구다. Obsidian은 노트·첨부·웹 페이지를 무한 공간에 배치하고 연결하는 기능을 공식 안내한다. 따라서 공간 배치만을 유일한 차별점으로 주장하기 어렵다. [Obsidian Canvas 공식 안내](https://obsidian.md/help/plugins/canvas)

**사업성 판단:** 제품 가치를 관찰하고 유입을 만드는 후보로 적합하다. 현재 수익 구조에서 개인 무료 사용의 인기만으로 독립 사업성을 판단할 수 없다.

## 5. 버전 B: 소규모 게임 개발팀

2~5명은 초기 탐색의 예시이며 실제 고객 규모를 확인한 결과가 아니다. 사용자는 팀원이고 구매자는 팀장·프로젝트 책임자일 것이라는 가설이다. 초보 기획자가 포함된 팀을 접근 가능한 첫 관찰 대상으로 삼을 수 있다.

### 비즈니스 모델 캔버스 B

| 구성 요소     | 초안                                                                                                           |

## 8. 고객군 비교와 현재의 판단

아래 비교는 시장 규모나 성공 확률을 계산한 결과가 아니다. 현재 제품·수익화 방향과 각 모델의 연결을 비교한 판단이다.

| 고객군             | 누가 비용을 내는가         | 현 BM과 연결                      | 가장 큰 미확인 조건                                     | 먼저 얻을 증거                                      |
| ------------------ | -------------------------- | --------------------------------- | ------------------------------------------------------- | --------------------------------------------------- |
| 개인 기획자·제작자 | 개인 단독 기본 사용은 무료 | 팀 유입 경로                      | 무료 사용이 팀의 공동 작업으로 이어지는가               | 다음 실제 기획 작업에서 반복 사용하고 팀원을 초대함 |
| 소규모 개발팀      | 팀장·프로젝트 책임자 가설  | 직접 연결                         | 기존 무료 도구 조합보다 공유 프로젝트가 충분히 유용한가 | 외부 팀의 실제 사용·결제·갱신                       |
| 교육기관·강사      | 강사·기관 구매자 가설      | 기간별 공유 공간으로 연결 가능    | 수업에 맞고 교사의 부담을 줄이는가                      | 실제 수업 파일럿과 재사용·유료 도입                 |
| 게임잼·워크숍      | 주최자 가설                | 행사 기간 공유 공간으로 연결 가능 | 무료 행사 도구에 더해 비용을 낼 제작·운영 가치가 있는가 | 범위가 정해진 유료 행사와 재계약                    |

**현재 권하는 탐색 순서:** 개인·동료 사용에서 실제 효용을 관찰하고, 작은 외부 게임팀에서 운영형 공유의 지불 의사를 확인한다. 교육·행사는 바로 접근 가능한 운영자가 있을 때 병행 후보로 둔다. 네 가지 상품을 동시에 개발하는 계획으로 해석하지 않는다.

지금 확인한 것은 창업자의 문제 경험, 제품의 제공 방향, 동료의 짧은 체험이다. 아직 확인하지 못한 것은 타인의 반복 사용과 구매다. 따라서 현재 평가는 **제품 가치 가설은 구체적이지만, 사업성 판단의 핵심인 유료 수요는 아직 미검증**이다. 사업성이 좋거나 나쁘다고 확정할 근거는 부족하다.

## 9. 사업 시작 전에 놓치기 쉬운 조건

| 점검할 조건                  | 현재 상태와 사업상의 의미                                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 무료 가치와 유료 가치의 연결 | 문서 배치·AI 시제품이 좋아도 공유 프로젝트를 살 이유는 별도로 증명해야 한다.                                                     |
| 고객의 기존 AI 환경          | 모든 사람이 AI를 구독한다고 가정하지 않는다. 지원 CLI 설치·인증·계정 사용 조건과 한도를 실제 사용자 환경에서 확인한다.           |
| 클라우드의 의미              | 서버를 우리가 운영해도 AI는 관리자 PC에서 실행한다. 관리자가 준비되지 않거나 PC가 꺼져 있을 때의 대기는 구매 기대와 맞아야 한다. |
| 사용자의 수준                | 초보에게 가치가 있을수록 설치·설명·실패 복구 지원이 많이 들 수 있다. 저렴한 구독료와 높은 지원 부담의 조합을 측정한다.           |
| 기존 대안                    | 공간형 문서 관리와 기존 AI 연결은 다른 도구에도 있다. 기능 존재보다 우리 흐름에서 작업이 얼마나 잘 이어지는지 확인한다.          |
| 실제 출시 준비               | 협업 기능의 존재와 상용 계정·결제·운영 준비 완료는 다르다. 제공할 상품과 현재 제공 가능한 범위를 맞춘다.                         |
| 운영 비용과 확장             | 서버 요금 외에 백업·복구·전송·결제·문의·개발 시간을 포함한다. 단일 서버의 실제 수용량은 미측정이다.                              |
| 프로젝트 종료                | 게임팀·수업·행사는 종료된다. 프로젝트 종료에 따른 구독 해지와 불만으로 인한 이탈을 구분하고, 보관·내보내기 정책을 설계한다.      |
| 고객 확보                    | 무료 사용자 총수 대신 실제 팀 초대·유료 전환·갱신과 확보에 쓰는 시간을 본다.                                                     |
| 제작 결과의 범위             | HTML 시제품과 상용 엔진 프로젝트·완성 게임을 구분한다. 실행 성공만으로 재미나 기획 품질을 보장하지 않는다.                       |

## 10. 지금 단계에서 필요한 작은 검증

다음은 제안이며 고객에게 연락하거나 유료 상품을 게시하지 않았다. 수량은 소규모 탐색 예시이고 통계적 시장 검증이나 보편적 성공 기준이 아니다.

1. **실제 작업 관찰:** 함께 개발하는 기획자가 해야 할 작업 하나를 정해 스스로 사용하게 하고, 막힌 지점·도움이 필요한 시간·완료한 결과를 기록한다. 칭찬보다 실제 완료와 다음 작업의 재사용을 본다.
2. **외부 팀의 공동 작업:** 창업자와 함께 개발하지 않는 작은 팀 3곳 정도에서 자료 작성→팀원 초대→시제품 확인→다음 수정까지 관찰한다. 무상이라면 유료 수요 증거로 분류하지 않는다.
3. **구매 행동 확인:** 운영 가능한 좁은 범위와 실제 가격을 제시해 결제·유료 파일럿 여부를 확인한다. 가격에 긍정적으로 답하는 것과 실제 구매를 구분한다.
4. **갱신과 원가 확인:** 다음 작업·다음 결제 기간에도 쓰는지, 팀별 인프라와 문의 시간이 얼마인지 측정한다. 기간이 끝난 수업·행사는 다음 회차 재계약으로 판단한다.
5. **결과에 따라 규모 선택:** 작은 수요와 낮은 지원 부담이면 부업 모델, 지속 유료 사용과 충분한 잔여 예산이면 1인 전업, 반복 판매와 운영 분담 근거가 생기면 고용 모델의 조건을 다시 계산한다.

고객군과 사업 규모를 정하기 위해 질문을 계속 늘리기보다, 현재 미확인 항목은 가설로 표시하고 위의 행동 근거로 갱신한다. 가격·과금 단위·지원 범위는 첫 유료 제안을 구체화할 때 결정한다.
