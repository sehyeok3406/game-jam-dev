# 0012 · 로컬 파일 휴지통

- 날짜 2026-11-12
- 상태 채택

## 문제와 결정

이미지 카드의 삭제가 설명 문서만 제거하면 가져온 원본이 프로젝트 폴더에 남는다. 홈 휴지통에서 로컬 파일의 복원 위치와 보관 기한을 확인할 수 있게 한다. 프로젝트 단위의 휴지통과 서버 수명 관리는 기존 경로를 사용한다.

- 로컬 삭제 계획은 삭제한 이미지 카드에서 원본을 찾는다. 살아 있는 Markdown·HTML·추적된 텍스트 리소스·제작 manifest에 같은 관리 파일 이름이 있으면 원본을 유지한다. 앱 밖의 파일과 동적으로 계산한 참조는 추적 범위 밖이다.
- 로컬 문서·에셋 노드와 추적된 HTML을 삭제하기 전에 프로젝트의 `.gamejam/local/file-trash/`에 한 삭제 명령의 변경 전후 데이터를 저장한다. 복제된 이미지의 원본은 활성 파일을 유지하면서 복원 사본에도 기록한다. 사운드·모델 원본은 기존 콘텐츠 주소 저장소에서 복원한다.
- `FileTrashService`는 기존 변경 적용과 편집 기록의 역변환·검증을 재사용한다. 홈은 등록된 로컬 프로젝트와 휴지통 ID로 요청하며 renderer가 경로를 지정하지 않는다. 원래 경로의 새 파일과 충돌하면 사본을 보존한다. 삭제의 실행 취소로 파일이 돌아오면 항목이 숨겨지고, 다시 실행하면 보관 기한까지 다시 나타난다.
- 프로젝트와 파일은 홈의 같은 대화상자에서 별도 탭으로 표시한다. 파일 사본은 7일 뒤 앱 시작 또는 실행 중 유지 작업에서 정리한다. 사용자가 일찍 제거해도 기존 편집 기록의 보관은 기존 정책을 따른다.
- 추적되지 않은 보조 파일이나 빈 폴더가 있는 HTML 결과는 기존 Windows 휴지통 경로를 유지한다. 공동 파일은 기존 서버 명령과 공동 편집 기록을 사용한다. 서버 원본의 참조·삭제 정책은 그대로 적용한다.

## 대안과 검증

OS 휴지통만 이용하면 홈에서 프로젝트별 목록을 만들거나 설명·원본·섹션의 동시 복원을 검증하기 어렵다. 편집 기록을 곧바로 휴지통 목록으로 쓰면 기존 기록의 보관 기간과 휴지통 기한이 결합된다. 프로젝트에 속한 복원 사본을 사용해 전체 프로젝트 이동·복원에도 사본이 따라가게 했다.

`tests/file-trash.test.mjs`와 `tests/file-trash-packaged.mjs`로 실제 경로 제거, 참조 보존, 이미지 복원, Undo/Redo, 충돌, 기한과 앱 재시작을 검증한다. `tests/project-trash.test.mjs`와 기존 Windows 홈 휴지통 검사로 프로젝트 보관 경로를 검증한다. 공동 파일 휴지통 또는 임의 HTML 결과 폴더를 앱에서 복원할 때 권한과 보관 형식을 다시 검토한다.
