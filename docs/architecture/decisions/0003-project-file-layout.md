# 0003 · 사용자 문서 통합과 프로젝트 파일 구조의 명시적 전환

- 날짜: 2026-10-30
- 상태: 채택, 구현 및 관련 검증 완료 (2026-10-31)
- 근거: 사용자 요청과 [구현 계획](../../plans/2026-10-30-project-file-layout.md)

## 문제

문서가 생성 경위에 따라 ideas, docs/imported, docs/copy, docs/versions 등에 분산되어 탐색기에서 찾기 어렵다. 사용자 문서와 HTML·캔버스 관리 정보 및 PC의 동기화·실행 기록도 섞여 있다. 여러 PC가 같은 공유 프로젝트를 쓰므로 앱 업데이트만으로 공동 경로를 바꾸면 구버전 쓰기와 미전송 변경을 잃을 수 있다.

## 결정

1. 새 프로젝트는 레이아웃 v2와 독립 이름 metadata로 시작하고 기본 Markdown 문서를 생성하지 않는다. v2 사용자 문서는 모두 docs 바로 아래에 저장한다. 종류·출처·묶음은 frontmatter로 관리한다. 제목은 초기 파일명에 사용하고 충돌은 짧은 ID로 해소한다. 제목 편집만으로 파일을 이동하지 않는다.
2. 실제 파일은 docs, assets, output, .gamejam으로 구분한다. .gamejam/project에는 캔버스·섹션·HTML 관리·작업 명세, .gamejam/local에는 개인 미리보기·로컬 히스토리·동기화·이전 기록을 둔다. 인증 자료는 기존 OS 암호화 저장소에 유지한다.
3. 서버 snapshot과 AI 명세의 내부 식별 경로(.canvas, .ai/tasks, sections, docs/html-sources 등)는 유지하고 filesystem adapter가 실제 .gamejam 경로로 변환한다. 사용자 문서 경로는 실제 docs 위치와 동일하다. 이 구분은 내부 UI에 새 개념으로 노출하지 않는다. AI의 격리 stage와 불변 history snapshot은 기존 식별 경로를 그대로 기록한다.
4. v1 프로젝트는 열기·업데이트·폴더 표시만으로 전환하지 않는다. ‘설정 및 도구 → 프로젝트 파일 구조 정리…’에서 실행한다. 공유 전환은 관리자만 기존 서버 FIFO 안에서 revision·편집 잠금·AI 실행/예약/요청을 검사한 뒤 한 번 확정한다. 새 서버 capability는 projectLayoutVersion: 2다. 새 형식을 생성하기 전 /health로 지원을 확인한다.
5. 논리 marker는 .canvas/layout.json, 실제 marker는 .gamejam/project/layout.json이다. marker에 version과 사용자 문서의 이전 경로표를 보관한다. 전환한 공유 프로젝트의 구버전 요청은 서버에서 업데이트 안내와 함께 거절한다. 이전 프로젝트의 통신·저장 계약은 유지한다.
6. 실제 파일 전환은 원본·대상 snapshot과 내부 원본 파일의 해시를 durable journal에 기록하고, 새 내부 파일 준비 → 사용자 자료·참조 반영 → marker 확정 → 검증된 이전 파일 정리 순서로 실행한다. marker 전 오류는 원본 내부 파일을 유지하며 journal에서 재개한다. marker 뒤에는 새 구조로 복구를 이어간다. 외부 변경·다른 대상 파일은 덮어쓰지 않는다. 완료 기록에도 이전 snapshot을 남긴다.
7. Markdown은 파싱한 링크 대상만 바꾸고 metadata의 경로 참조를 갱신한다. 문서 ID·알 수 없는 속성·본문·섹션 소속·상대 이미지 링크를 보존한다. 원본 history는 재작성하지 않고 복원/Undo 시 현재 경로로 해석한다. 내용 변화가 없는 JSON의 원래 직렬화도 유지한다.
8. 뒤늦게 접속한 PC의 오프라인 초안은 서버의 경로표로 base/local을 함께 변환하고 기존 3-way merge·충돌 처리로 보존한다. 서버에 없던 미전송 신규 문서도 ID와 제목으로 안전한 docs 경로를 할당한다. durable 문서 저장 큐도 enqueue/전송 시 현재 경로표를 적용하되 저장 ID·시도·기준 revision·본문을 유지한다. 자동 반영할 수 없는 온라인 전용 작업은 기존 오류·보존 흐름을 유지한다.
9. 홈의 ‘탐색기에서 표시’는 해당 프로젝트의 PC 사본을 기존 mirror로 준비한 뒤 루트를 연다. 현재 프로젝트를 전환하지 않는다. 오프라인 초안·캐시를 보존하며 권한 회수는 캐시 성공으로 위장하지 않는다. 이미 v2인 PC 사본에 오래된 v1 snapshot을 적용하지 않는다.

## 대안과 영향

- 내부 식별 경로까지 모두 바꾸는 안은 AI 명세·history·서버 속성 키를 광범위하게 바꿔야 하므로 채택하지 않았다. filesystem 경계를 통해 탐색기 구조를 단순화하고 기존 식별 계약을 보존한다.
- 모든 프로젝트의 자동 전환은 여러 PC와 미전송 수정의 안전성 때문에 채택하지 않았다.
- HTML 분류/버전 체계와 이미지 형식은 유지한다. 캐시 GC, 임의 파일 이동 감지, 새 분류 UI는 이 변경 범위가 아니다.
- .gamejam 전체를 지워도 되는 캐시로 취급하지 않는다. 그림·게임 UI 원본·미전송 변경·복구 자료가 포함된다.
- 여러 파일과 서버/PC를 하나의 원자 트랜잭션이라고 주장하지 않는다. 서버의 durable 확정과 PC 사본 준비를 구분한다.

## 검증

project-layout 단위·실제 임시 서버 검사, 기존 생성·편집·복사·AI·Undo·모드 전환·휴지통 검사, Windows 패키지의 홈 메뉴·설정 대화상자·재시작 검사를 사용한다. Project-PP 실자료와 다른 사용자의 PC는 검증에 사용하지 않는다. 결과는 구현 계획서에 기록한다.
